# DAM2 (Data Assets Management 2) 产品需求文档

## 产品背景

DAM2 是一款面向游戏开发者的本地轻量级资源管理与检索工具，旨在帮助开发者集中管理分布于多个硬盘的游戏资产。随着项目推进，游戏美术、音频、3D 模型、UI 素材、插件脚本等资源会日积月累地存储在不同磁盘和文件夹中，传统的文件夹管理和操作系统检索难以满足高效查找的需求。现有部分数字资产管理工具（如设计领域的 Eagle、3D 资源管理工具 Connecter 等）提供了标签和预览功能，但往往局限于单一类型或需要云端支持，不完全符合游戏开发者在本地离线、多类型资产统一管理方面的需求。DAM2 应运而生，其目标是在离线环境下提供对海量分散资产的快速索引和模糊搜索，以及基本的预览和标签管理能力，帮助开发者提升查找效率并减少重复下载或制作资源的情况。

## 核心功能模块

-   多硬盘资源库管理：支持配置多个硬盘或分区作为资源库根路径。每个硬盘资源库在系统中有独立标识，应用在启动时扫描检测硬盘挂载变化。如某资源库所在硬盘未连接，应用界面中仍允许检索出该库的资源条目但标记为离线（无法预览原始文件），提示用户连接硬盘或更新盘符映射。提供手动盘符/路径映射管理界面，用户可在硬盘卷标或盘符改变时重新指定资源库的新路径，使已有索引数据与文件重新关联。
-   资产类型支持：支持以下游戏常用资产类型的导入与管理：
    -   图像：如.png、.jpg、.jpeg、.bmp、.tga 等格式的图片资源（不生成缩略图，仅记录基本信息和路径）。
    -   音频：如.mp3、.wav、.ogg 等音频文件，可在应用内播放预览。
    -   3D 模型：常见 3D 模型格式如.fbx、.obj、.gltf/.glb、.dae 等，使用 Three.js 加载以提供交互式预览[1]。对于需要材质的格式（如 OBJ+MTL），要求相关文件在同一目录或压缩包内。预览采用 WebGL 技术实现，支持基本的模型旋转、缩放操作。
    -   UI 资源：界面素材，如矢量图标、UI 元素贴图（通常也是图像文件），以及可能的 UI 布局文件（如特定引擎的 UI 预制件）。UI 资源主要以图像方式呈现，在应用内直接查看原图。
    -   插件脚本/插件包：包括 Unity 的 .unitypackage 包、Unreal Engine 插件（通常为含 .uplugin 的压缩包或文件夹）、DCC 工具（如 Maya、3ds Max、Blender 等）的插件和脚本文件（格式如 .py、.mll、.mel 等）。这些以文件形式存储的插件资源会纳入索引管理，但一般无法直接在应用中预览其功能，仅提供基本信息展示。
-   非支持类型：不支持纯视频类资产（如 .mp4、.avi 等视频文件）的管理与预览。这些文件在扫描时将被忽略或过滤，不纳入资产库索引。
-   资产索引与导入规则：应用通过遍历用户指定的资源库路径，对符合支持类型的文件建立索引记录。索引信息包括文件名称、扩展名、文件路径（或所在硬盘及相对路径）、文件类型（依据扩展名归类，如图像/音频/模型等）、文件大小、创建或修改时间等元数据，以及标签集合等。文件类型严格通过扩展名判断，若文件缺失扩展名则跳过导入并在扫描日志中记录（防止无法识别类型的文件进入库）。索引过程支持增量更新：即新增文件或修改文件时可以更新数据库记录（可在启动时或用户手动触发下执行重新扫描）。预期支持索引规模在几十万条记录级别，需确保索引过程和后续查询的性能。
-   压缩包支持：应用内置对常见压缩文件格式（如 .zip、.rar、.7z、.tar.gz 等）的读取解析模块。无需解压整个压缩包，即可索引其中的文件条目：在扫描阶段，若检测到支持类型的压缩包文件，则打开包体读取其内部目录结构，将其中符合资产类型的文件视作独立资产记录建立索引。索引记录需包含这些文件的路径定位信息（例如记录逻辑路径为“archive.zip:/folder1/asset.png”形式，或通过单独字段标识所属压缩包及内部相对路径）。用户在搜索结果中看到压缩包内资产时，应用应提示其来源于压缩文件。资产详情查看时，应用实时从压缩包中提取原始文件内容用于预览（临时解压单个文件到内存或本地缓存目录）。该机制保证用户可直接预览压缩包内资产，而不必手动解压。压缩包索引功能需要考虑性能和稳定性：对大型压缩包仅提取文件列表而不解压全部内容，必要时对非常大的包可以设置大小阈值或提示用户。
-   搜索与筛选：提供强大的本地搜索功能，包括多种维度的筛选与排序：
    -   文本模糊搜索：支持中英文关键字的模糊匹配检索。用户可输入资产名称关键词（不区分大小写），应用通过 SQLite 全文检索或索引机制匹配包含该字符串的名称或标签，实现即时联想与结果反馈。中文支持拼音模糊匹配和部分汉字匹配，英文支持部分单词匹配和模糊查询，满足用户以不完整的名称定位资产的需求。
    -   标签过滤：支持按资产标签筛选。用户可以在搜索条件中指定一个或多个标签，结果仅显示包含这些标签的资产。标签搜索对中英文均适用（结合 AI 翻译标签，实现中英文同义标签统一检索）。
    -   类型筛选：提供按资产类型过滤的选项（例如复选框或下拉多选），可以只看图像或只看音频等。
    -   硬盘/库筛选：支持按资源库来源过滤，用户可以选择一个或多个硬盘库，仅查看来自所选库的资产。
    -   排序：提供按照名称、文件大小、日期等字段排序结果的功能。默认排序可按相关度或名称升序，用户可切换排序方式。
    -   分页与懒加载：采用无限滚动（Infinite Scroll）机制加载结果。初次检索显示前若干条，用户滚动列表到底部时自动加载更多，直到显示全部匹配项。这样避免一次性加载大量结果造成界面卡顿，并保持应用响应流畅。
-   标签与 AI 辅助：每个资产支持用户自定义标签，数量上限为 20 个标签/资产。标签用于对资产内容或用途进行标注，如“角色”、“UI 按钮”、“环境音效”等，增强搜索精确度。除了手工管理标签，应用集成 AI 辅助功能：针对文件英文名称，调用第三方 AI 模型接口（如 OpenAI GPT 系列模型或国内的 DeepSeek 模型等）来自动生成标签和中文翻译。具体流程为：在资产导入索引时，如果文件名主要为英文，应用可调用 AI 接口分析文件名字符串，返回若干关键词标签和对应的人类可读中文翻译。生成的标签将附加到资产记录中（需经用户确认或编辑），中文翻译则存储为资产的别名以支持中文检索。所有 AI 生成请求结果在本地缓存（例如保存在数据库字段或单独的缓存表中），对相同的文件名不重复调用接口，以降低延迟和 API 费用。用户需在应用设置中配置 AI API Key 才能启用此功能；若未配置，则跳过 AI 标签生成但不影响其他功能。出于性能考虑，大批量文件的 AI 标签生成可在后台线程分批完成，并在界面上以标记或通知形式提示用户哪些资产已生成了 AI 标签。
-   资产预览：提供针对不同类型资产的原生预览能力，方便用户在无需打开外部软件的情况下快速阅览文件内容：
    -   图像预览：在资产详情界面直接显示原始图像（以实际分辨率适应窗口缩放展示）。由于列表中不生成缩略图，首次打开详情时可能稍有延迟（根据图像大小），但能确保看到完整细节和颜色，无压缩损失。
    -   音频预览：内置音频播放器控件，支持播放常见格式音频。用户可在详情界面播放/暂停，查看音轨时长等。音频解码利用 Electron/浏览器的 HTML5 音频能力或 Node 模块，无需外部播放器。
    -   3D 模型预览：采用 Three.js 库加载 3D 模型文件，在详情界面渲染交互式的三维视图[1]。支持用户控制视角旋转、缩放模型，以及基本的灯光和材质显示。对于复杂模型（高面数或含大纹理），需在加载时进行优化处理（如使用 Three.js 自带的简化器或仅加载 LOD 较低的版本）。3D 预览模块重点支持常见格式，可能不涵盖全部模型类型（例如.blend 原始文件不直接支持，需要用户自行转换为支持格式）。
    -   插件/其他文件：对于代码脚本类文件（如.txt、.cs、.py 等），详情界面可使用文本高亮显示内容（若适用）；而像 UnityPackage 这类专有格式，由于本身也是压缩包，可视为文件集合，不直接打开（或将 UnityPackage 当作 zip 读取显示内部文件列表，但不解析其二进制内容）。对于无法直接预览的插件文件，可提供选项“打开所在目录”，以便用户用相应专业软件查看。
-   启动同步与离线处理：应用在每次启动时自动检查各资源库路径状态：当某个已建库的硬盘未连接或路径不存在时，标记该库为不可用但保留其索引数据。对于此类库的资产，在搜索结果中仍会列出（方便用户了解该资源存在于哪个硬盘），但禁止打开详情预览，取而代之显示“文件不可访问，资源库未连接”的提示。用户可在稍后连接相应硬盘后重新尝试访问，无需重建索引。此机制保证即使部分库离线也能进行全局搜索，在集中检索和硬盘物理分离之间取得平衡。应用也提供手动刷新功能，让用户在硬盘重新接入后触发一次库同步，更新状态。
-   数据存储与配置：所有资产索引和元数据存储在本地 SQLite 数据库中。数据库模式设计支持多硬盘、多类型资产的同时管理，例如：
    -   一个表保存资源库信息（库 ID、路径、标识符如盘符或卷序列号等）。
    -   一个主资产表，包含资产 ID、名称、扩展名、类型、所在资源库 ID、相对路径（或完整路径）、文件大小、修改时间等字段。
    -   标签关联表，将资产 ID 与标签文本关联（每条记录一个标签，或采用逗号分隔存储标签列表亦可，根据查询需求选择设计）。
    -   可能的全文检索虚表，用于加速名称和标签的模糊查询（利用 SQLite FTS5）。
    -   AI 缓存表或字段，存储资产的 AI 生成标签和翻译，以避免重复请求。 数据库文件默认保存在用户本地应用数据目录，但应用提供设置选项允许用户自定义数据库文件的存储路径（例如将数据库放在某高速硬盘或指定位置）。这一功能便于在不同机器间迁移配置或根据需要备份/共享索引数据。

## 架构选型

-   技术栈：DAM2 选择 Electron + React + Ant Design + SQLite 作为主要技术栈，符合桌面跨平台和快速开发要求。
    -   Electron：负责应用主进程和桌面容器。Electron 让我们使用 Web 技术构建跨平台桌面应用，减少针对不同操作系统的重复开发。它内置 Chromium 浏览器和 Node.js，便于集成文件系统操作和界面展示。本项目需要直接访问本地文件、执行文件扫描和调用本地库（如压缩包解析库），Electron 的 Node 环境非常适合这类本地 IO 密集型应用。
    -   React + Ant Design：在渲染进程中使用 React 框架构建前端界面，利用其组件化和虚拟 DOM 提高开发效率和界面性能。Ant Design 组件库提供丰富的现成 UI 组件和整洁美观的设计风格，适合工具类应用界面需求。例如，我们将使用 Ant Design 的布局、菜单、表格/List、标签、输入框、下拉等组件来快速搭建一致的交互界面，减少造轮子时间。
    -   SQLite 数据库：作为本地数据存储方案。SQLite 轻量、嵌入式、零配置，支持 SQL 查询和事务，非常适合桌面应用保存结构化数据[2]。索引几十万条记录在 SQLite 可轻松应对，并可借助其全文检索扩展满足模糊查询需求。事实上，大部分桌面应用都倾向于在客户端使用 SQLite 保存数据[2]。我们将在 Electron 主进程通过 Node.js 的 sqlite3 或 better-sqlite3 驱动与数据库交互，承担数据读写和查询任务。相比浏览器内置的 IndexedDB，选择 SQLite 便于直接编写复杂查询、调优索引，并可让用户轻松备份单一数据库文件。
    -   压缩包解析：考虑使用 Node.js 社区成熟库，如 adm-zip（支持 zip）、node-unrar、7zip-min 等，来读取各种压缩格式的文件列表和内容。这些库用 C/C++实现底层解压逻辑，通过 Node 模块调用可获得接近原生的性能。由于 Electron 允许调用原生模块，整合这些库实现对压缩包的无缝支持成为可能。我们会将压缩包读取操作放在主进程或后台线程，以避免阻塞前端 UI。
    -   Three.js：作为 3D 模型预览的核心引擎，其与 Web 技术天然兼容。通过 React 与 Three.js 集成（如使用 Three.js 提供的 GLTFLoader、OBJLoader 等），我们可以在 Electron 中渲染 3D 内容。Three.js 支持多种 3D 模型格式和丰富的渲染功能，足以满足预览需求[1]。在实现中，会封装一个预览组件，当用户打开模型详情时在 React 组件里挂载一个 Three.js 场景进行显示。
    -   AI 接口调用：通过 HTTP 请求调用第三方 AI 服务，如 OpenAI 的 REST API 或国内模型的 API。由于这些调用可能涉及敏感的 Key 和网络请求，我们将在主进程实现 AI Service 模块，负责读取配置的 API Key、与远程服务通讯并返回结果。为安全和稳定起见，对 AI 请求增加超时和错误处理，以及本地结果缓存。
-   模块划分与通信：应用将划分为前后端两部分： - 前端（Renderer）：基于 React 构建的 UI 层，负责呈现搜索界面、列表和详情等，处理用户交互。通过 IPC（进程间通信）向主进程请求执行扫描、查询数据库、读取文件等操作。 - 后端（Main）：Electron 主进程负责系统交互和数据处理。包含子模块：文件扫描模块（递归遍历硬盘目录，读取文件信息和调用压缩包解析）、数据库模块（封装 SQLite 的读写和查询）、AI 模块（负责与 AI 服务通信）、预览辅助模块（如通过 Node 文件系统读取图片、音频数据流供前端展示）。主进程根据来自前端的 IPC 请求，调用相应模块执行操作，并将结果（如查询结果集、文件二进制数据流）发送回前端。
    这样的架构确保 UI 渲染与重度 IO 操作解耦，提升应用响应速度，也利用了 Electron 擅长的多线程/异步能力。

## UI 概述

DAM2 的用户界面将注重简洁直观，方便开发者快速上手。采用 Ant Design 风格，使布局和控件保持一致。主要界面和交互包含：

-   主窗口布局：顶部为全局搜索栏和工具栏区域；左侧为可选的过滤面板；主要区域为搜索结果列表；右侧或弹出对话框用于显示选中资产的详情。
-   顶部栏包含：全局搜索输入框（占据主要宽度，支持实时搜索提示）、一个下拉菜单或图标按钮用于过滤条件（点击弹出筛选项，如类型、硬盘、多标签选择等），以及“设置”按钮入口。
-   左侧过滤面板（可折叠）：列出可选的筛选条件，如多个硬盘库的勾选列表，资产类型勾选项，标签列表（常用标签或者标签云）等。用户在此勾选或输入筛选条件，主列表随之更新。
-   主列表区域：采用列表或表格视图按行展示资产条目。每行显示关键字段：文件名、类型（以文字或类型图标表示）、所在硬盘库标识（如磁盘名称）、文件大小、修改日期、已有标签等。由于不显示缩略图，列表呈现将更像文件管理器的细节视图，以文本信息为主。列表支持点击表头排序（如按名称或日期排序）。使用无限滚动加载时，可在列表底部显示加载中提示，滚动到新区域时追加渲染项。
-   列表交互：用户可选中某一行（单击高亮），然后触发查看详情；或右键弹出菜单，提供快速操作如“打开所在文件夹”、“复制文件路径”、“编辑标签”等。对于离线状态的资产，在列表中会以灰色或禁用样式显示，并可能有离线图标提示。
-   资产详情界面：当用户选中某资产，界面会打开一个详情视图（设计上可为侧边滑出面板，或模态弹窗，也可在主区域切换显示）。详情界面内容根据资产类型有所不同：
-   上方显示资产基本信息：文件名（若有中文翻译可一起显示）、类型、大小、分辨率/时长（如适用）、所在路径（硬盘/文件夹/压缩包路径）、创建/修改日期等。
-   中间是预览区域：
    -   图像：显示图片本身（背景黑色或网格底，以突出透明度效果），并提供缩放查看原始尺寸的功能。
    -   音频：显示一个波形或音频图标，提供播放控件（播放/暂停按钮、进度条、音量控制）。
    -   3D 模型：嵌入一个画布展示 Three.js 渲染的模型，可以交互（鼠标拖拽旋转、滚轮缩放）。可能需要“全屏查看”按钮以便更大区域预览。
    -   其他不可预览文件：显示文件图标及提示“无法预览”，提供打开外部的按钮。
-   下方是标签和操作区：列出当前资产的标签（生成的和手动的），标签以可交互的 badge 样式显示。用户可在此添加新标签（输入后回车生成，限制最多 20 个），或删除已有标签（点击标签旁的删除按钮）。如果资产有 AI 生成的建议标签且尚未确认，可能以半透明样式显示，用户可以一键“接受所有 AI 标签”或者逐个添加。该区域也显示 AI 生成的中文名称（翻译）供参考编辑。
-   底部操作按钮：如“在资源管理器中打开”（打开文件所在目录并选中文件）、“用默认程序打开文件”、以及关闭详情视图的按钮。
-   设置界面：通过主界面顶部的“设置”按钮进入独立页面或对话框。设置内容包括：
-   管理资源库：列出当前添加的硬盘库路径，显示状态（在线/离线）。提供添加新库（选择文件夹路径）和删除库的操作。对于已存在的库，可编辑其标识（自定义名称）或手动更新路径映射（当硬盘盘符变化时使用）。
-   AI 服务配置：输入或修改 AI API Key、选择使用的模型服务（例如 OpenAI 或 DeepSeek），以及清除本地缓存的选项。
-   数据库配置：显示当前 SQLite 数据库文件路径及大小，提供修改存储路径的功能（更改后需重启应用生效），以及导出/备份数据库的按钮。
-   其他：常规设置如开机启动开关、界面语言切换（中/英），更新检查等。
-   错误与提示：UI 将包括一些用户提示：如当某次搜索结果为空时，显示“未找到符合条件的资产”；当硬盘离线访问详情时，提示“资源不可用，请连接硬盘 X”；在 AI 标签生成时，如果未配置 API 则提示用户设置。如果压缩包内容无法读取或损坏，会弹出警告提示该资产无法预览。所有提示信息确保中英文兼备，友好明了。

总体来说，UI 设计遵循简洁实用原则，将搜索功能置于核心位置，周边辅以筛选和标签管理。通过合理的布局和交互，用户能快速在庞大的资产库中定位所需资源，同时对资产细节一目了然。

## 数据库与压缩包策略

-   数据库结构：DAM2 采用 SQLite 作为本地数据库，库结构围绕多硬盘和多类型资产的需要进行设计，确保数据组织清晰、高效查询和易扩展。主要库表及策略如下：
    -   资源库表 (repositories)：字段包括 repo_id（主键）、name（库名称或硬盘标识，如盘符）、base_path（根路径）、status（当前状态：在线/离线）、last_scanned（上次扫描时间）等。每个已添加的硬盘/路径在此有一条记录，用于管理盘符映射和状态监控。应用启动时对比 base_path 是否存在以更新 status 字段。
    -   资产主表 (assets)：存储所有资产条目。核心字段：
        -   asset_id（主键）、
        -   repo_id（所属资源库，外键关联 repositories 表）、
        -   name（文件名，不含路径）、
        -   extension（扩展名，用于快速类型判断）、
        -   type（资产类型类别，可根据扩展名映射，如“image”“audio”等）、
        -   path（文件路径：对普通文件为相对库的路径，对压缩包内文件则可格式化存储为“压缩包文件路径::内部路径”或用两个字段表示）、
        -   size（文件大小）、
        -   modified_time（修改时间戳）、
        -   tags_cached（标签字符串缓存，可存所有标签拼接用于全文搜索）、
        -   ai_translated_name（AI 生成的中文译名，可用于搜索）。 根据需要可以拆分一些数据到子表，例如标签独立表或路径独立表等，但由于 SQLite 本地性能较高，适度的冗余如在主表存缓存字段可以加速查询。
    -   标签表 (tags 或 asset_tags)：若采用独立标签表，每条记录包含 asset_id 和 tag 文本，用于资产-标签的多对多关系。此外，可对 tag 列建立索引以加速标签筛选查询。上限 20 个标签的限制可由应用层控制（超过则不允许新增）。
    -   全文检索虚表：利用 SQLite FTS5 建立虚拟表，例如 assets_fts，包含需要搜索的文本字段（如文件名、译名、标签）。每当资产表更新时同步更新 FTS 表，以支持模糊查询。在查询时，对用户输入做分词（英文按空格、中文可按拼音或通过定制分词器）后匹配 FTS 表，得到相关资产 ID 列表，再去主表获取详情。
-   索引策略：为保证查询性能，数据库需要对常用查询字段建立索引：
    -   对 assets.name（或 FTS 替代）、assets.extension、assets.type、assets.repo_id 等建立索引，以支持名称模糊、类型筛选、库筛选等条件的快速执行。
    -   标签如独立表，可对 tag 字段和 asset_id 字段分别建索引，以快速通过标签找资产，或判断某资产是否有某标签。
    -   repo_id 以及 path 也可建索引，方便定位特定路径资源用于去重或更新检查。
-   压缩包索引表示：对于压缩包内部资产，我们选择不在数据库中建立单独的表，而是将其视同普通资产，但存储方式略作特殊处理：
    -   path 字段记录时，可将压缩包文件路径和内部文件路径结合。例如在 Windows 环境，可用约定符号比如||隔开：“D:\assets\archive1.zip||models/tree.fbx”。在应用层解析该字段时，如果检测到包含||则识别前半部分为实际压缩包文件路径，后半部分为内部路径。
    -   另一个方式是在 assets 表增加字段 is_archive（布尔）和 parent_archive_path（如适用）。如果 is_archive 为 false，则 path 正常表示文件路径；若 true，则当前记录代表一个压缩包本身（但通常我们不将压缩包作为资源，只索引内部资源）。或者增加 archive_id 来关联资源库中某压缩包文件记录。不过为了简化，实现中可以不将压缩包作为单独资产类型，而直接在扫描时展开其内部文件作为资产，parent_archive_path 记录压缩包来源。这种设计方便搜索时无需特别区分，但在展示时可以通过检查该字段来追加“来自压缩包”的信息。
-   压缩文件扫描：扫描器遇到压缩包文件时，使用相应库列出其内容列表。对于每个内部文件条目，判断其扩展名是否受支持，如果是则在数据库中新增资产记录。内部文件的元数据获取包括文件名、大小、可能的修改时间（若压缩格式提供）等，但没有独立的真实路径，只能通过压缩包路径+内部路径定位。可以为压缩包内容生成一个虚拟的相对路径表示（如上述的 archive.zip||inner/path/file.ext 保存进 path 字段）。
-   更新与删除：需要考虑，当用户删除或移动了压缩包文件时，其内部资产应该一并失效。应用在启动或定期校验时，如果发现数据库中记录的某压缩包文件不存在，则可批量清除其内部资产记录（或标记为离线类似硬盘离线处理）。因此在数据库中可以通过 parent_archive_path 快速查询属于该压缩包的所有资产进行维护。
-   数据库维护：由于资产规模大，需提供一定的维护机制：
    -   提供数据库重建/重索引功能：当数据出现大量冗余（比如很多文件已删除但数据库仍有记录）时，用户可触发一次彻底重扫，重置数据库内容。
    -   定期（或手动）清理无效记录：比如硬盘库永久移除时，可以删除对应 repo 以及旗下资产记录；当压缩包或文件消失时，清理记录等。
    -   数据库备份：因为用户可能在标签和 AI 注释上投入精力，提供备份/恢复数据库的简易方法（如导出 SQL 或复制.db 文件等）保证数据安全。

## 性能预期

DAM2 在性能上需要达到较高标准，以应对几十万规模资产的管理，同时保证本地应用的流畅体验。

### 索引和查询性能

-   初始索引：针对首次添加一个大型资源库（假设包含 20 万文件）的完全扫描，应在可接受的时间内完成。理想目标是在 SSD 硬盘上每分钟扫描数万文件条目，包括访问文件系统和写入数据库的操作。如果全库扫描需耗时较久（例如一两个小时），应在 UI 上给予进度反馈并允许随时暂停/继续。后续增量扫描则更快，仅处理变化部分。
-   查询速度：利用 SQLite 索引和全文检索，实现亚秒级的查询响应。在拥有 20 万记录、每条包含名称和标签的数据库中，模糊搜索一个关键词应该在 100 毫秒级别返回结果集（SQLite 经优化和在本地运行可满足此要求）。即使加上 UI 渲染时间，总体搜索体验应接近实时：用户输入每个字符后，结果列表迅速刷新。为此需确保：
    -   数据库的查询在后台线程执行，查询结果数量过多时仅提取前若干条迅速显示，其余异步加载。
    -   FTS 索引对于中文能正确分词（或预先存储拼音辅助检索），避免全表扫描。
-   内存占用：由于不保存图像缩略图且采用按需加载列表，应用运行时内存主要来源于 Electron 自身和已加载的数据。预期在典型使用下（几十万记录，结果列表显示上千项）内存占用控制在几百 MB 量级。大型 3D 模型预览时显存占用可能上升，但可以在模型窗口关闭时释放资源。
-   前端流畅度：React 界面操作（如切换筛选、滚动列表）应保持流畅。无限滚动加载通过批次渲染和虚拟列表技术，保证即使结果很多也不会一次性渲染所有 DOM 元素。滚动过程帧率应稳定在 60FPS 左右，无明显卡顿。
-   磁盘与 CPU 负载：在扫描或复杂查询时，SQLite 和压缩解析可能产生较高 IO 和 CPU 使用。应用应合理调度这些任务，如采用批处理、添加适当的延时或 yield，防止长时间 100%占用单核。压缩包解析尤其在读取大文件时要避免阻塞 UI 线程。利用 Electron 多线程或子进程执行 heavy tasks（如使用 worker_threads 或 child_process）确保主线程响应。
-   并发：通常桌面单用户应用不存在多并发修改问题，但需考虑同时进行的操作：例如用户可能一边扫描新库，一边在搜索使用应用。我们需确保数据库写入与读取不会互相饿死锁死。SQLite 本身支持并发读，但写是排他锁，我们可以在扫描批量插入时间隙性地提交事务，以便查询不被长时间阻塞。同时，UI 上可以告知用户扫描进行中搜索结果可能不完全或略有延迟。

总体而言，性能目标是在“大数据量本地查询”方面达到媲美专业工具的水准，让用户几乎感觉不到延迟。通过合理的索引、优化的数据库操作和异步架构，DAM2 即便在资产数量达数十万时，也能保证搜索秒出结果，界面交互流畅，预览加载迅速。

## 风险说明

在项目实现过程中，需要注意并提前规划以下风险及挑战：

-   文件系统变化风险：用户可能在应用外部移动、重命名或删除资产文件，导致数据库索引与实际文件不同步。特别是在多硬盘场景下，这种变化难以实时监控。若索引不更新，将出现搜索结果点击后文件不存在的情况。对此，我们通过启动扫描和手动刷新来定期同步可能的改动。但仍有风险是用户在两次同步间移动了文件。我们考虑在打开详情时再次校验文件存在性并处理异常。如果文件缺失则提示用户刷新索引。
-   硬盘路径变更风险：Windows 环境下硬盘盘符可能变化，或者网络映射盘符失效。虽然提供了手动盘符映射，但如果用户未及时调整，可能出现大量资产暂时无法访问。这个风险在设计上已通过“离线库”机制处理：即使盘符变化导致路径不通，我们保留索引并提示用户修复路径。仍需注意避免用户误操作导致错误的映射覆盖正确数据 —— 例如要求在更改库路径时验证新路径内容与原索引的一致性（如通过硬盘序列号或目录结构简单比对），降低误配风险。
-   压缩包处理风险：对多种压缩格式的支持需要依赖第三方库，不同库质量各异：
-   可能遇到解压库 Bug 或兼容性问题，对于非常新的格式或加密压缩包无法处理。我们需要限制支持范围（如不支持加密压缩包，或提示用户解密后导入）。
-   大文件性能：一个压缩包内若含成千上万文件，索引会耗费时间且占用内存。我们需优化读取策略（例如分块读取目录，或对超大压缩包设置跳过或特殊处理）。如果使用 7zip 库，可以利用其流式读取能力。
-   内容预览：提取压缩包内文件可能临时占用磁盘空间（若写入缓存文件）或内存，对大文件（如高分辨模型贴图）要注意释放。风险在于未及时释放可能导致应用占用膨胀甚至崩溃。需确保预览结束后关闭压缩包流和清理缓存。
-   AI 功能风险：
-   依赖外部服务：AI 标签生成需要调用外部 API，存在网络不稳定、服务响应慢甚至无法访问的情况。如果过于依赖 AI 结果，可能影响用户体验。我们必须将 AI 功能设计为可选和非阻塞：即使 AI 服务不可用，应用主体（检索、预览）也能正常运行。对于请求超时要做好处理（跳过或重试几次后放弃，并通知用户）。
-   API 成本：调用第三方模型可能产生费用，如果用户一次导入海量资源而全部请求 AI，将带来成本和速度压力。这是风险也是用户需要知晓的限制。我们在文档中和 UI 上需明确提示 AI 调用可能的费用，并提供选项让用户选择针对新导入文件批量生成或手动触发，避免不必要的开销。
-   标签准确性：AI 根据文件名生成的标签和翻译有可能不准确或不符合预期。如果用户完全信任 AI 结果，可能导致检索误导。因此我们将 AI 生成的内容仅作为建议，鼓励用户审核和修改。这仍然存在 AI 给出不恰当词语的风险，需要用户把关。
-   性能风险：虽然目标制定了高性能要求，但实际实现中可能遇到:
-   数据库膨胀：几十万记录加上全文索引，数据库文件可能达到数百 MB 甚至更大。如果 SQLite 查询优化不足，查询速度可能下降。我们需按需调整索引和查询策略。风险在于超出预期规模时性能劣化，需要预留优化空间（比如拆库或者引入额外的缓存层）。
-   Electron 内存/资源占用：Electron 应用相对原生较重，如果同时打开多个大型预览（如几个高模 3D 模型），内存和 GPU 占用上升，存在应用崩溃或卡死风险。必须限制同时打开的预览数量（例如详情窗口一次只显示一个）并在关闭时销毁释放 Three.js 资源和 revoke 图像 URL 对象等。
-   多线程复杂度：为了保持流畅，我们会使用多线程或异步任务。Electron 多线程模型下，主进程、渲染进程、worker 线程之间通信复杂，处理不当可能引发线程不同步、数据竞争等 Bug。尤其数据库在多线程访问时要注意串行化。对此需严格设计线程模型和使用队列锁机制来避免竞争风险。
-   功能取舍风险：由于明确不做某些功能（多人协作、云同步、引擎集成），可能有用户希望这些功能。这本身不算实现风险，但在需求管理上需要清晰界定，以免开发中尝试增加超出范围的功能导致延期或质量问题。因此必须控制范围，对任何超出本 PRD 定义的需求变更严格评估。

## 非功能边界

DAM2 聚焦于离线单机环境下的资产管理，不涉及协作和云端，因此在非功能性方面需明确边界，防止误用或过高期望：

-   单用户应用：不支持多人同时操作同一资产库。没有用户权限管理或并发编辑机制。所有功能假定单一用户独占地管理本地资源。如需团队共享，应各自维护各自的数据库，或手动交换数据库文件。
-   无云同步/备份：应用不提供云端备份或多设备同步功能。资产文件及索引数据库的安全由用户自行负责。本地硬盘损坏或丢失将导致资产无法访问，DAM2 无法从云恢复。未来如需支持云，要另行设计，不在本版本范围。
-   无游戏引擎直接集成：DAM2 不是特定游戏引擎（Unity/UE 等）的插件，也不直接与引擎资产库交互。开发者需手动从 DAM2 定位文件，然后导入到游戏工程中。DAM2 不会自动同步游戏项目内的资源变动。例如在 Unity 内删除了某素材，DAM2 索引不会自动受影响（除非该文件也在索引库路径下）。
-   非版本控制或发布工具：DAM2 不具备版本管理、文件锁定、流程审批等高级功能。它并非 Perforce、Git 或云 DAM 系统的替代品，而是专注于本地搜索与预览。对需要版本追踪的，美术资源仍应使用专门的版本控制系统。
-   不支持视频和特殊格式：正如前述，视频文件不在支持范围。同时一些特殊的或专有的文件格式（例如 Photoshop .psd 文件预览、CAD 文件等）可能无法预览或检索其内部内容。DAM2 对于未知扩展名一律不导入，也不会尝试解析文件内容来猜测类型。这是为了保证系统稳定和简洁。
-   有限的可扩展性：由于使用 SQLite 和 Electron，本应用适用于小型到中型规模的数据。如果资产规模达到数百万级记录或需要更复杂的查询分析，SQLite 可能力不从心，Electron 的性能也会遇到瓶颈。在这种极端情况下，DAM2 可能不是理想方案，需要迁移到更专业的解决方案。但对于预期的几十万规模，其性能和功能是充分且高效的。

通过上述边界描述，用户可以了解 DAM2 专注解决的问题和不涉足的领域，从而合理期望应用的作用，将其用在合适的场景中。

## 未来扩展建议

在当前产品定位基础上，未来版本的 DAM2 可以考虑拓展以下功能和改进，以满足更广泛或深入的需求：

-   云同步与协作：引入云端支持，实现资产索引和标签的备份同步。可以开发一个云端组件，将 SQLite 索引上传至服务器，不同设备间同步更新。进一步可支持团队协作：如多个用户共享一个资产库的索引和标签，共同维护标签体系。在权限控制上，可考虑只读共享（他人只能搜索不能改标签）或完全共享模式。协作功能的加入将使 DAM2 从单机工具进化为小团队的协同资产管理平台。
-   引擎集成：提供与 Unity、Unreal 等游戏引擎的集成插件或接口。例如开发 Unity 编辑器插件，可在 Unity 内直接调用 DAM2 的搜索接口，选中资产后一键导入到 Unity 项目的 Assets 目录。Unreal 引擎可通过定义资产源来引用 DAM2 索引。同样，可以开放 DAM2 的 API 或命令行，使外部程序（包括脚本）能够查询资产位置，以便在各种工具链中集成。
-   支持视频预览：将来可考虑有限支持视频类型资产的管理和简单预览。通过集成视频解码库或利用浏览器<video>元素，可以预览常见格式短视频。这对存放动画素材或剪辑的用户会有帮助。不过视频文件通常较大，索引和缩略处理需谨慎，以防数据量爆炸。
-   缩略图和图库视图：虽然当前出于性能考虑禁用了列表中的缩略图，但未来可作为可选功能提供。例如允许用户切换“图库视图”，在结果中显示图片/模型的小缩略图进行视觉浏览。实现上可建立缩略图缓存（生成较小分辨率的图像），并提供缓存管理。对于 3D 模型，也可在索引时预生成预览截图。缩略图模式将极大提升对美术素材的浏览体验，但需要权衡生成时间和存储开销，适合在性能优化后推出。
-   更丰富的预览支持：扩展预览格式和信息：比如对 PSD、AI 等设计稿生成预览图，对材质贴图识别其类型（法线、粗糙度等）并成组显示，对音频生成波形图或支持播放节选，对 3D 模型显示其材质列表和多 LOD 切换等。这些改进让 DAM2 不仅是索引工具，更是一个简易的数字资产浏览器。
-   智能化功能：进一步利用 AI 提高效率：
-   图像内容识别：结合计算机视觉模型，对导入的图片自动生成内容标签（例如“森林”、“角色”、“建筑”），而不仅依赖文件名【由于目前仅通过文件名生成标签，增加视觉识别将更全面】。
-   相似资产查找：提供“查找相似”功能，对于选中的一张图片或一个模型，通过 AI 特征向量比对，在库中找到相似风格或相近内容的其他资产。这对于美术设计挑选素材很有价值。
-   自动分类：AI 根据资产的属性（名称、内容）建议分类归档，例如自动把某些文件归入“环境音效”或“角色模型”类别标签中，减少用户手工整理负担。
-   性能与技术升级：随着数据规模增长，可能需要升级底层架构：
-   数据库方面，可探索引入更加高效的搜索引擎或 NoSQL 方案。例如如果索引过百万，考虑 ElasticSearch 本地集成用于全文检索，或切换到更高性能的嵌入式数据库（如 DuckDB、LevelDB 等）作为可选项。
-   桌面架构方面，留意 Electron 的替代或升级，比如使用 Electron 新特性 (如 v13 引入的 InkRenderer) 或探索基于 WebAssembly 的性能提升方案。同时关注内存泄漏优化、垃圾回收调优，保证大数据处理更稳健。
-   更友好的用户体验：根据用户反馈不断改进：
-   界面支持深色模式、主题切换，提升美观度。
-   提供快捷键操作，如快速聚焦搜索框，全局快捷键呼出应用等，方便高频使用。
-   增加教程或引导，帮助新用户上手高级功能（如标签技巧、搜索语法等）。
-   多语言支持扩展到更多语言，以便国际用户使用（当前中英双语基础上，未来可支持日语、韩语等游戏开发常用语言社区）。

以上扩展建议为 DAM2 指出了清晰的演进路径。初始版本聚焦核心检索与管理功能，未来可按优先级逐步加入这些特性，持续提升产品价值，满足更广泛的数字资产管理需求。
